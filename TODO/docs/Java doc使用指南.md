# JavaDoc 使用指南（编写方法与语法）

> 面向刚写完第一个 Java 程序的人（本文以本项目 `TODO` 的 `TODOList.java` 为例子）
>
> 阅读前提：已经写过基本的类、方法、字段，想给自己的代码加上"会说话的注释"。

---

## 0. 先把神秘感去掉

JavaDoc 不是一种语言，它**只是注释**。区别在于：

- 普通注释 `//` 和 `/* */` 是给**人**看的，编译器直接忽略。
- JavaDoc 注释 `/** */` 也是给人看的，但 IDE 和 `javadoc` 工具**认识它**，能把它自动整理成一份网页说明书（HTML）。

也就是说：**JavaDoc 写对了，等于白得一份免费的项目文档。**

在 IntelliJ IDEA 里，把光标放到方法上按 `Ctrl + Q`，就能看到 JavaDoc 渲染出来的效果；不写也能看到签名，但写了才"讲得清"。

---

## 1. JavaDoc 注释长什么样

JavaDoc 注释一定要用 `/**` 开头、用 `*/` 结尾，并且**写在一个元素的上方**（类、方法、字段、构造方法的前一行）。

```java
/**
 * 向清单的末尾添加事项
 * @param event 事项的实例
 */
public void addEvent(TODOEvent event){
    event.setNo(TODOList.size());
    TODOList.add(event);
}
```

三处必须注意：

1. 开头是 `/**`，不是 `/*`，也不是 `//`。
2. 每个 `*` 前面通常对齐（IDEA 会自动补），数量不强制，但整洁。
3. 一定要**紧贴**在被注释元素**上一层**，中间不能空行、不能隔着别的代码，否则 JavaDoc 会"贴错人"。

---

## 2. 核心语法：两部分

一份 JavaDoc 由**普通描述 + 标签（tag）**两部分组成。

### 2.1 描述部分（写人话的地方）

`@` 符号之前的内容，是描述部分。它负责回答"这个东西是干嘛的"。

```java
/**
 * 通过现成的列表生成，调用该方法会直接覆盖原有内容<br>
 * 该方法会自动依照事项在列表中的位置重写事项的编号
 */
public void loadTODOList(List<TODOEvent> TODOList) {
```

常用的小技巧：

| 写法 | 作用 |
| --- | --- |
| `<br>` | 手动换行（普通换行会被 javadoc 吞并成一行） |
| `{@code 代码}` | 把内容当代码显示，并**自动转义**尖括号，不会报错 |
| `{@link 目标}` | 生成一个可点击跳转的链接 |
| 直接用汉字 | 能在说明里随便写，重点讲清楚**前因后果** |

> **反例**：描述部分只写"这个方法是干嘛的"，跟没写一样。好的 JavaDoc 描述会讲：什么场景调用、调用后有什么副作用、结果长什么样。比如上面那句"会直接覆盖原有内容"，这句才是真正重要的信息。

## 3. 常用标签（@tag）全解

标签都以 `@` 开头，一般放在描述部分**之后**，每个占一行。

### 3.1 `@param 参数名 说明` —— 方法的参数

写清楚每个参数**叫什么、是什么、有没有限制**。

```java
/**
 * 向清单的指定位置插入事项
 * @param event 事项的实例
 * @param no 位置
 */
public void addEvent(TODOEvent event, int no){
```

> **关键**：`@param` 后面的名字**必须和真实参数名完全一致**。写错或用 `@param e` 代替 `@param event`，IDE 会直接飘黄线报警。

### 3.2 `@return 说明` —— 方法的返回值

**只有有返回值的方法**才写 `@return`；返回 `void` 的方法不能用它。

```java
/**
 * 检查清单里是否有指定位置的记录
 * @return 该位置是否存在事项
 */
public boolean hasEvent(int no) {
```

### 3.3 `@throws 异常类型 触发场景` —— 可能抛出的异常

告诉调用的人：**什么情况下这个方法会炸**，提前做好准备。

```java
/**
 * 保存当前清单到磁盘
 * @throws StorageException 当文件无法写入时抛出
 */
```

### 3.4 `@see 引用` —— 给一个相关链接

指向本类或其他类的方法，一般配合 `{@link}` 用。实际中使用频率不高。

```java
/**
 * 读取整个清单
 * @see #loadTODOList(List)
 */
```

### 3.5 `@since 版本` / `@version 版本` / `@author 作者`

记录版本演进和作者。养成习惯，追责方便（开玩笑的），主要方便回溯。

```java
/**
 * @author 张三
 * @version 1.0
 * @since 2026-10-07
 */
```

## 4. 字段和类的 JavaDoc

方法不是唯一能写 JavaDoc 的地方，**字段、类、构造方法**一样能写。

### 4.1 字段

尤其适合解释"这个字段有什么用、能不能改"。

```java
/**
 * 清单id
 * 这个是只读的，不允许修改
 */
private int id;
```

### 4.2 类

类注释写清楚：这个类是什么、谁来用、核心职责是什么。

```java
/**
 * 表示一个待办清单。
 * 内部维护一组 {@link TODOEvent}。
 */
public class TODOList {
```

### 4.3 构造方法

记录构造参数的含义，比如随机 id 的生成逻辑。

```java
/**
 * 构造函数
 * @param name 清单名
 */
TODOList(String name){
```

## 5. 进阶语法：`{...}` 内联标签

内联标签嵌在描述部分里面，用花括号包起来，最后以英文 `}` 结束。最常用两个：

| 内联标签 | 作用 | 示例 |
| --- | --- | --- |
| `{@code ...}` | 显示代码，`<`、`>` 不会被解析成 HTML | `{@code no > 0}` |
| `{@link ...}` | 生成可点击的类/方法链接 | `{@link TODOEvent}` |

```java
/**
 * 检查编号是否合法，要求 {@code no >= 0}
 * 相关类见 {@link TODOEvent}
 */
```

> **为什么一定要用 `{@code}` 而不是直接写 `>`？**
> 因为 JavaDoc 最终会被当 HTML 渲染。直接写 `<` 会被当成 HTML 标签，导致内容错乱甚至被吞掉。用 `{@code}` 就安全了。

---

## 6. IDEA 偷懒大法：自动生成模板

手写很累？IDEA 能一键生成。

1. 在方法上方输入 `/**` 然后按 **回车**，IDEA 会自动根据方法签名补全所有 `@param`、`@return`、`@throws` 的空壳。
2. 还能自定义模板（设置 → Editor → File and Code Templates / Live Templates），比如字段模板带 `@author`。

> 这只是"生成壳"，**壳里的文字还是要你自己写**。JavaDoc 的价值永远在描述部分的人话，不在标签的数量。

---

## 7. 五条最重要的心法（记不住就记这几条）

1. **`/**` 是 JavaDoc，`//` 和 `/*` 不是。** 用对符号，工具才认你。
2. **写在元素正上方，中间不能空行。** 否则注释"贴错人"。
3. **`@param` 名字必须和参数真名一模一样。** 错一个字母就报警。
4. **有返回就写 `@return`，可能抛异常就写 `@throws`，`void` 不写 `@return`。**
5. **少写"干嘛"，多写"为什么"。** JavaDoc 最大的价值是告诉后来人（包括你）那些**代码已经讲不清的规则和副作用**——比如 `loadTODOList` 会覆盖原内容。

## 8. 光写不生成等于没用：跑一次 `javadoc`

写完后，用命令把注释变成真正的网页文档：

```bash
javadoc -d doc src/main/java/**/*.java -encoding UTF-8 -charset UTF-8
```

- `-d doc`：输出到一个 `doc` 文件夹。
- `-encoding UTF-8 -charset UTF-8`：**一定要加**，否则中文注释会乱码。
- `src/main/java/**/*.java`：告诉它扫描哪些源文件。

生成后打开 `doc/index.html`，就能在浏览器里看到自己项目的说明书了。

---

> 一句话总结：**JavaDoc 是"写给人看、工具能读"的注释。它不改变程序行为，却决定了你的代码以后好不好用、好不好查、好不好交接。**
